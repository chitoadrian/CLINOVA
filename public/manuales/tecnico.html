Arquitectura y continuidad

Borrador técnico · CLINOVA 0.4.0 · Semana 4. Continúa el código integrado de Semana 3. No cambia las credenciales ni el proyecto Supabase; las pruebas de carga se ejecutan con datos aislados.

Archivos principales

src/db.ts: fachada común; selecciona Web o IPC de Tauri. src/core/web.ts: autenticación y base IndexedDB. src/core/week3.ts: operaciones clínicas y cola. src/sync-engine.ts: conexión, reintentos y estados. src/components/ClinicalModule.tsx: formularios de ambas áreas.

src-tauri/src/clinic.rs y clinic/week3.rs implementan el servicio SQLite. supabase/schema.sql y supabase/functions/clinova-api/ conservan el esquema y la API. tests/ incluye regresión, carga e inyección de fallos.

Modelo local

Roles, usuarios y credenciales se relacionan con las atenciones del paciente. Signos, triage, evaluaciones y objetivos iniciales mantienen las relaciones anteriores. Kardex, camas, ingresos, rutinas y evolución se representan como documentos clínicos tipados, con referencias y validaciones.

La estructura SQLite no es idéntica a los almacenes IndexedDB ni al agregado JSONB cloud. La fachada comparte operaciones y reglas, no archivos físicos de base de datos.

Instalación y compilaciones

Web local

Requisitos: Node.js 22.12 o posterior y npm. Desde proyecto/: npm ci, npm run dev. Abrir http://127.0.0.1:1420/. En PowerShell se puede usar npm.cmd.

Producción: npm run build; después npm run preview -- --port 4174. Abrir http://127.0.0.1:4174/. No ejecutar index.html con doble clic. La caché offline se instala después de una primera carga con conexión.

Windows

Instalar Rust con destino MSVC, Microsoft C++ Build Tools con desarrollo de escritorio C++ y Windows SDK; disponer de WebView2. Ejecutar npm run desktop:build -- --bundles nsis,msi. Los paquetes se generan en src-tauri/target/release/bundle/.

Linux

En Ubuntu 22.04/24.04 instalar Rust, Node y dependencias: libwebkit2gtk-4.1-dev, build-essential, curl, wget, file, libxdo-dev, libssl-dev, librsvg2-dev, libayatana-appindicator3-dev y patchelf. Ejecutar npm ci y npm run desktop:build -- --bundles deb,appimage.

El workflow .github/workflows/escritorio.yml prepara Windows y Linux cuando se ejecuta en un repositorio autorizado. Los scripts scripts/build-windows.ps1 y scripts/build-linux.sh incluyen comprobaciones previas. Su presencia no significa que ya existan instaladores.

Transacciones e integridad

Cada modificación clínica guarda el documento y su pendiente en la misma transacción. Si falla la cola, no se confirma el paciente. Una edición incluye la versión local: las versiones obsoletas se rechazan. La baja es lógica, con deleted_at y conservación de historial.

SQLite activa foreign_keys, WAL y busy_timeout. Índices únicos impiden códigos de cama repetidos y dos ingresos activos para la misma cama o paciente. IndexedDB comprueba reglas equivalentes durante la transacción de escritura.

Conservación de datos

Web guarda por origen y perfil: cambiar puerto o navegador crea otro almacenamiento. SQLite se guarda como clinova.sqlite3 en el directorio app_data_dir de Tauri. Para respaldarlo, cerrar la aplicación antes de copiar la base y revisar posibles archivos WAL/SHM.

No se implementó exportación/restauración de respaldos desde la interfaz. La sincronización no sustituye una política de copias de seguridad; no borres bases con cambios pendientes.

Intercambio y seguridad

Secuencia del intercambio

El motor toma hasta 50 operaciones ordenadas por dependencias y envía op_id, UUID y revisión base con una sesión cloud válida. Comprueba cambios al guardar, al volver la red, al recuperar visibilidad y cada cinco segundos. Ante fallos aplica espera creciente, hasta 60 segundos.

La API valida la identidad y el rol activo; PostgreSQL confirma versiones y registra recibos idempotentes. El cliente retira solo el op_id confirmado. Si hubo otra edición mientras esperaba, mantiene la operación nueva y actualiza su revisión base.

La recepción usa un cursor y confirma cambios locales antes de avanzarlo. Una revisión remota diferente conserva ambas versiones y bloquea la operación hasta resolver. El archivo guarda la decisión; elegir local genera otro op_id sobre la revisión remota.

Autenticación y autorización

Las credenciales locales usan PBKDF2-HMAC-SHA256, 600.000 iteraciones y sal individual. Cinco fallos bloquean cinco minutos. La sesión permanece en memoria, vence por inactividad y tiene límite total. La actividad de sincronización no mantiene abierta la sesión local.

La API existente verifica el usuario con Supabase Auth y consulta su membresía activa; no acepta como autoridad un rol enviado por la interfaz. RLS está activo en el esquema privado. La clave publicable puede estar en el cliente; la clave de servicio permanece en el servidor.

Límites que deben comunicarse

La base local no está cifrada en reposo. Un usuario con control del dispositivo puede manipularla. Desactivar una cuenta local no desactiva automáticamente su membresía cloud. Las cuentas locales y cloud requieren administración coordinada.

Referencia oficial de autenticación de funciones: https://supabase.com/docs/guides/functions/auth. No se cambiaron políticas ni datos remotos en las pruebas de Semana 4.

Repetir pruebas y preparar la revisión

Comandos

npm test: regresión, permisos, módulos, cola, conflictos y nueva batería QA. python tests/test_sqlite.py: seis migraciones, cuentas e integridad. npm run build: compilación Web. Guarda siempre salida y código de terminación.

Para la prueba de navegador, instala la dependencia de pruebas indicada en tests/README_QA.md, inicia Vite en 1424 y ejecuta node tests/browser-qa.mjs. Usa Edge con un contexto nuevo. Todas las peticiones al proyecto Supabase se interceptan; no se genera carga en la base real.

Qué cubren las pruebas

500 altas en ráfagas de 20, 50 lecturas de 500 fichas, escrituras concurrentes, rollback ante fallo de cola, respuesta remota no autorizada y confirmaciones duplicadas. En Edge: cuatro roles, 250 fichas en IndexedDB real, formulario offline, reingreso, HTTP 503, recuperación y recepción independiente.

Revisión con otro grupo

Entrega el proyecto y la ficha de pruebas a un grupo revisor. Deben anotar equipo, integrantes, versión, pasos, resultado observado y evidencia. No se considera ejecutada una revisión cruzada solo por pasar las pruebas automatizadas.
